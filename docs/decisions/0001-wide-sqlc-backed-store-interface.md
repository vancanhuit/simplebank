# ADR-0001: Wide sqlc-backed `Store` interface

## Status
Accepted

## Date
2026-07-15

## Context
Data access goes through `store.Store` (`internal/db/store.go`), which embeds
the sqlc-generated `sqlcdb.Querier` (one method per query) plus three
hand-written transaction methods: `TransferTx`, `CreateUserTx`, and
`VerifyEmailTx`. `Querier` is regenerated by sqlc from `internal/db/query/*.sql`.

The interface is therefore *wide*: a handler that needs two queries still
depends, at the type level, on every generated method. In tests, `fakeStore`
embeds a nil `store.Store` and overrides only the methods a given test
exercises; any un-stubbed call panics. Multiple architecture reviews have
flagged this width and proposed segmenting `Store` into per-handler role
interfaces (`accountStore`, `transferStore`, …).

## Decision
Keep a single wide `Store` interface backed by the generated `Querier`. Do not
segment it into role interfaces at the current size of the service.

## Alternatives Considered

### Segment into role interfaces (interface segregation)
- Pros: each handler depends on a narrow seam; test doubles implement only what
  they use, with no nil-embed panic fallback.
- Cons: the generated `Querier` is the source of leverage — one code-gen step
  yields every query. Segmenting means hand-maintaining N interface
  declarations that must track the generated surface. At this service's size
  (a handful of handlers) it spreads interface declarations without reducing
  the number of concepts a reader must hold.
- Rejected: cost exceeds benefit today. Revisit if the handler count grows
  enough that individual handlers depend on genuinely disjoint slices, or if
  the nil-embed test pattern starts hiding real coupling.

### Wrap `Querier` behind bespoke narrowing interfaces per package
- Pros: hides sqlc from callers.
- Cons: pure indirection; the methods pass straight through. Adds a shallow
  layer with no behavior of its own.
- Rejected: fails the deletion test — removing the wrapper concentrates no
  complexity, it just removes a pass-through.

## Consequences
- Adding a query is a single sqlc regeneration; no interface bookkeeping.
- Test doubles use the embed-nil-and-override pattern; an unexpected store call
  surfaces as a panic, which is the intended signal.
- The three `*Tx` methods remain the deep part of the seam: they hide `execTx`,
  multi-step ordering, and deadlock-safe lock ordering behind one call each.
- Architecture reviews should treat interface width here as an accepted
  sqlc trade-off, not a defect, and cite this ADR rather than re-proposing
  segmentation.
